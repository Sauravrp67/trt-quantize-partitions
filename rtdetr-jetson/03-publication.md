# Shared Publication Template (all three scaffolds)

## 1. Write-up skeleton (blog post or long README)

1. **The question** — one sentence, falsifiable. ("What control rate can a $249 board actually close?" / "Where do RT-DETR's milliseconds go on an SoC?" / "What does a ggml port cost vs TRT-LLM, really?")
2. **Hardware + environment lockdown** — JetPack/TRT/container digests, power mode, clocks, fan, ambient. One table.
3. **Methodology before results** — parity rules / frequency math / attribution method. This section is the brand.
4. **Results** — headline chart first, tables after, raw CSVs linked. p50/p95/p99, sustained-vs-burst.
5. **The failures** — what broke, what you did, what you'd tell the vendor. Often the most-read section; never cut it.
6. **What this predicts** — one paragraph generalizing beyond the benchmark (e.g., "any DETR on Orin will hit X because Y").
7. **Repro** — clean-clone instructions verified on the board before Monday.

## 2. Rules

- Every chart regenerated by a script from CSVs. No hand-made figures.
- Negative results stay in. Cliffs and autopsies are product, not embarrassment.
- The novelty sentence matches the research pass's verdict — cite-and-extend or first-to-our-knowledge-with-search-documented. Never bare "first".
- License note in the repo README — verified 2026-09-15: YOLO26 is **AGPL-3.0**/Enterprise; **RF-DETR's license is UNKNOWN** (the Apache-2.0 assumption was refuted 0-3 in verification — read the LICENSE file the day you start); disclose model licenses next to results so employers can tell what's deployable.
